# MoonCAS 设计说明

## 解决的问题

MoonCAS 为字节内容生成稳定的 SHA-256 标识，并把去重、校验、引用保护和分块复用组合成一组后端无关的语义。它位于文件系统或对象存储之上，不负责 S3、R2 等厂商 API。

## 数据路径

1. `put` 计算输入的 SHA-256，以小写十六进制摘要作为键。
2. 相同内容得到相同键，后一次写入不会增加逻辑对象数量。
3. `put_verified` 比较调用方声明的摘要和实际摘要，不一致时不写入。
4. `get` 返回完整字节；`verify` 重新计算摘要，用于发现内容损坏。

`Digest` 的字段不公开。调用方可以保存、比较和显示摘要，但不能绕过哈希过程构造一个与内容无关的标识。

## 引用与回收

`pin` 表示仍有一个使用者依赖对象，`unpin` 释放一次引用。只要引用存在，`delete` 就拒绝删除；`collect` 仅清理没有引用的对象。这是刻意保守的第一版模型，不是完整的对象图可达性分析。

分块对象在创建时为每个块持有一次引用。调用方不再需要清单时，先调用 `unpin_chunked`，再调用 `collect`。重复块虽然只存储一次，但每个清单仍各自持有引用。

## 为什么使用固定大小分块

固定大小分块的边界容易复现，也便于验证分块顺序、缺块失败和引用释放。它的缺点是文件头部插入数据后，后续块边界都会移动。内容定义分块可改善这种情况，但需要额外滚动哈希、参数选择和性能测试，不纳入 0.1.0。

## 当前边界

- `MemoryStore` 只适合测试、示例和临时缓存；进程退出后数据消失。
- 当前 API 对完整输入计算摘要，没有流式哈希接口。
- 分块清单由调用方持有，尚未序列化并作为内容寻址对象保存。
- 不提供并发事务、分布式一致性、访问控制或加密。
- SHA-256 用于内容身份和完整性校验，但不会自动证明内容来自可信发布者。

下一阶段应优先增加文件系统后端、原子落盘和持久化清单，再根据基准数据考虑流式哈希及内容定义分块。
